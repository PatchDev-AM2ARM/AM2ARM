Code conventions for the modern .13 projects

Engine and scope
Use the pinned modern GameMaker runtime's semantics. Related global functions
may share a Script asset. Keep startup code outside function declarations in its
existing execution position. A script function runs in the caller's scope; a
method is bound to an instance or struct. Converting between them is a behavior
change, not a cosmetic cleanup.

Existing names are interfaces
Preserve asset names, GML function signatures, saved option keys, language keys,
Android extension exports and numeric bridge commands. Legacy numeric resource
references and imported __ compatibility helpers remain in place. New resources
use the existing s/o/sh/font/rm prefixes as appropriate and descriptive names.
Do not rename fields without checking variable/string lookups and persistence.
New Script asset names must also avoid existing variable names: a container name
can affect identifier resolution even when its functions have different names.

Formatting and naming
New port functions use snake_case. Keep the port modules' _snake_case convention
for parameters and temporary locals; keep existing instance/global field names.
Use descriptive UPPER_CASE names for new constants and four-space indentation.
Opening braces follow the declaration/condition in the port helpers. Preserve
the surrounding style when making a small change inside inherited gameplay.
Avoid unrelated whole-project reformatting. Wrap explanatory comments so the
meaning remains visible without horizontal scrolling.

Responsibilities
Group functions by the state and behavior they serve, rather than by line count.
Document the expected caller, coordinate space and ownership at module boundaries.
Keep event handlers as the recognizable entry points. Preserve their event category
and invocation order when extracting helper functions. Direct calls in per-frame
code remain direct; do not introduce allocating callback wrappers for tidiness.

Comments and editor help
Use English comments to explain constraints and decisions. Use GameMaker JSDoc
descriptions, parameters, return values and caller context when these help someone
use an entry point correctly. Do not repeat every statement in prose. Preserve
notes about particle RNG consumption, cache generations, display context changes,
shader fallbacks and other behavior that a simplified-looking rewrite could lose.

Rendering and lifetime
Name the owner of surfaces, buffers and cached data. Keep invalidation/recreation
and release paths discoverable. Surfaces can be lost on resume. Restore render
targets and GPU/draw state according to the caller's existing contract. Do not
add per-frame allocation, file reads or extra synchronization to a formatting pass.

Localization and platforms
New user-facing captions use the shared localization helpers. Preserve stable
selector indices and original font behavior. Check dual_enabled where one screen
and two differ, and global.android_app where Android and gmloader-next do:
os_type is os_android in both.

Verification
Separate organizational edits from gameplay or performance changes. For declaration
moves, check original function contents, calling scope, resource registration and
event callers. Exercise affected flows with one screen and two. For rendering,
compare actual output; a successful compile alone does not prove visual parity.
